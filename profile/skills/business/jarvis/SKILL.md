# Джарвис — трёхролевой мультиагентный пайплайн

Пайплайн для **важных сложных задач Алексея** (сметы ремонта, анализ лотов,
контент-планы, сложные расчёты, документы). Дорогая модель тратится ТОЛЬКО
на постановку задачи; дешёвая делает основную работу; средняя проверяет.

## Когда включать (триггер)

- Алексей пишет: «прогони через Джарвиса», «используй Джарвис», «через Джарвис»
- Задача дорогая/важная по оценке агента: ошибка стоит денег или времени,
  нужен вдумчивый анализ, задача больше «быстрого ответа»

**НЕ включать** для мелочей (ответ на письмо, короткий вопрос, быстрый факт) —
оверхед из 3 моделей убивает смысл на стыках.

## Роли и модели (выбор Алексея, зафиксирован)

| Роль | Модель | Ум (AA) | Вход $/M | Когда вызывается |
|---|---|---|---|---|
| 🧠 Мозг (постановка) | `openai/gpt-5.6-sol` | 60.9 | 2.5 | 1 раз в начале — генерация SPEC |
| 🛠️ Исполнитель | `deepseek/deepseek-v4-flash-0731` | ~48 | 0.14 | основной объём работы |
| 🔍 Проверяющий | `google/gemini-3.7-flash` | 56.0 | 0.375 | сверка по чек-листу, ≤2 итерации |

Правило ролей: **проверяющий УМНЕЕ исполнителя** (56 > 48) — иначе он
пропустит ошибки работяги. Мозг вызывается редко (доли цента), поэтому Sol
допустим даже при входе $2.5/M.

## Реализация в Hermes

**Вариант A (рекомендуемый):** субагенты по умолчанию наследуют родительскую
модель. НЕ менять `delegation.model` глобально (сломает vision-субагентов —
DeepSeek text-only!). Вместо этого:

1. **Мозг** — отдельный разовый вызов:
   `hermes chat -q -m openai/gpt-5.6-sol "Сформируй SPEC по шаблону: ..."` (промпт со вставленным шаблоном ниже + контекст задачи). Парсить вывод как SPEC.
2. **Исполнитель** — `delegate_task` с полным SPEC в goal/context
   (субагент наследует Gemini — приемлемо, но если нужен именно DeepSeek,
   запустить фоном: `hermes chat -q -m deepseek/deepseek-v4-flash-0731 "<SPEC> Сделай ТОЛЬКО п.3-4"`).
3. **Проверяющий** — агент (текущая основная модель Gemini 3.7 Flash) сам
   сверяет артефакт с чек-листом SPEC. PASS → сдать Алексею; FAIL → правки
   исполнителю (максимум 2 круга), после чего эскалация к Мозгу (Sol) с
   описанием, что пошло не так.

## Шаблон SPEC (обязателен к заполнению Мозгом)

```
SPEC
1. ЦЕЛЬ      — измеримая, 1–2 предложения («посчитать смету ремонта <адрес>
               с точностью ±10%»)
2. КОНТЕКСТ  — что уже известно: файлы, факты, ссылки, цифры
3. ЗАДАЧИ    — конкретные шаги для ИСПОЛНИТЕЛЯ по пунктам, без «и т.д.»
4. АРТЕФАКТ  — что на выходе: файл/таблица/структура ответа (формат!)
5. ЧЕК-ЛИСТ  — критерии приёмки «да/нет» (ТЗ для ПРОВЕРЯЮЩЕГО)
6. ГРАНИЦЫ   — чего НЕ делать, бюджет, срок
7. ЯЗЫК      — русский, стиль, объём
```

Мозг не должен выдавать общие слова — требовать заполненной SPEC целиком.
Если Мозг уклоняется («сделай хорошо»), повторить с требованием конкретики.

## Процесс (коротко)

1. Получить задачу от Алексея → оценить: важна? → Джарвис.
2. Мозг (Sol) → SPEC.
3. Исполнитель → артефакт по п.3–4.
4. Проверяющий → чек-лист п.5: PASS / FAIL + правки.
5. Доработка ≤2 раундов → иначе эскалация к Sol.
6. Сдать результат Алексею кратко: что сделано, где артефакт, что проверено.

## Pitfalls

- Исполнитель импровизирует → жёстко требовать «только п.3-4», без самодеятельности.
- Мозг размазывает формулировку → требовать SPEC целиком, все 7 полей.
- Проверяющий «кивает» (всё ок без проверки) → сверять ПО ПУНКТАМ чек-листа и
  показывать Алексею, что именно проверено.
- Гнать мелочь через Джарвис → не экономия, а расход (3 вызова вместо 1).

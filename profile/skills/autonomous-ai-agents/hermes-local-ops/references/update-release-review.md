# Проверка изменений Hermes Desktop после обновления

Применяй, когда Алексей спрашивает «что нового/полезного после обновления?». Цель — кратко отделить то, что реально установлено, от общего списка релиза, а затем объяснить пользу для его текущих проектов.

## Порядок проверки

1. **Установи фактическую версию исходников.** Найди актуальный каталог Hermes под `HERMES_HOME`, затем проверь текущую ревизию и дату последнего коммита в локальном checkout:
   ```bash
   git -C "C:/Users/Administrator/AppData/Local/hermes/hermes-agent" log -1 --format="%h %cs %s"
   git -C "C:/Users/Administrator/AppData/Local/hermes/hermes-agent" status --short
   ```
   Если путь профиля другой, подставь обнаруженный абсолютный путь; не предполагай, что любой `hermes` в PATH указывает на активный Desktop checkout.

2. **Отдельно проверь время сборки интерфейса.** Прочитай абсолютные файлы `desktop-build-stamp.json` и, если есть, `web-ui-build-stamp.json` в активном `HERMES_HOME`. Сопоставь build timestamp с последним commit checkout: код движка и собранный интерфейс могут быть обновлены не одновременно. Не выдавай функции исходников после даты сборки UI за гарантированно видимые в Desktop.

3. **Бери ТОЧНУЮ локальную дельту — это первоисточник, а не release notes.** Цепочку версий даёт лог самой установки:
   ```bash
   grep -aoE 'v0\.[0-9.]+\+[0-9]+\.g[0-9a-f]+ → v0\.[0-9.]+\+[0-9]+\.g[0-9a-f]+' logs/update.log | tail -8
   ```
   Последняя строка — пара `<старый_sha> → <новый_sha>` (то же в `logs/update_receipts/`). Дальше разложи дельту по типам и подсистемам:
   ```bash
   git -C "…/hermes-agent" log <old>..<new> --no-merges --format='%s' | grep -E '^(feat|fix)\('
   git -C "…/hermes-agent" log <old>..<new> --no-merges --oneline -- apps/desktop
   ```
   **Не используй `git log --since='N days ago'`** на этом репозитории: он отдаёт тысячи коммитов (репо очень активен), окно задаётся ровно парой SHA. Учти схему версии `vX.Y.Z+<N>.g<sha>`: `<N>` — число коммитов от ближайшего тега, поэтому один и тот же `<sha>` встречается и как `v0.21.5+9318.g302c5d9`, и как `v0.21.6+138.g302c5d9` — сверяйся по SHA, не по числу. Сверку с официальными релизами (`github.com/NousResearch/hermes-agent/releases`, docs) держи как дополнение: локальный checkout может быть новее опубликованного релиза.

4. **Сделай персональный отбор.** Сначала перечисли 3–6 подтверждённых изменений, которые реально полезны Алексею: Desktop-workflow, проекты Фрунзе 17, ресёрч недвижимости, подготовка артефактов, модели/субагенты или локальная надёжность. Отделяй пользовательские функции от исправлений и инфраструктуры. Указывай конкретное применение, а не длинный changelog.

5. **Дай безопасный следующий шаг, не меняя систему.** Можно предложить проверить или попробовать конкретную функцию; не создавать проекты, ботов, MCP-подключения, расписания и не менять настройки без запроса. Сохраняй уже принятые ограничения проекта — например, не запускать отложенный скоринг до завершения ремонта.

## Правила точности

- Не трактуй число «обновлений», коммитов, файлов или PR как число новых функций: цифры релиза описывают объём изменений, а не пользовательские возможности.
- Явно называй границы знания: локальный checkout, Desktop/UI build stamp, последний опубликованный upstream release — это три разные точки.
- Если локальная ревизия новее последнего опубликованного релиза, сообщи об этом и не приписывай промежуточному коду релизную стабильность.
- Пиши по-русски, на «ты», деловым коротким форматом: сначала вывод, потом наиболее полезное для Алексея, затем важная оговорка. Добавь ссылки на официальные источники.
